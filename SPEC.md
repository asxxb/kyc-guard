

## 1. Project Summary

**KYC-Guard** is a real-time customer-screening and financial-risk platform. It does what a bank's compliance engineering team does, at small scale.

**One-line pitch:** *Screens new customers against sanctions and PEP lists in real time, scores their risk with explainable reasons, monitors their transactions for suspicious patterns, and gives analysts a case queue to review.*

**Why it exists (for the README):** Banks must verify who their customers are (KYC, Know Your Customer), screen them against sanctions lists, and watch for money-laundering patterns (AML). This project shows how to build that with event-driven Java microservices, search, streaming and auditability.

**Data rule:** Use **synthetic data only**. Never include real personal data. Sanctions and PEP lists are generated by a data generator (Section 11).

## 2. Goals and Non-Goals

### Goals
- Production-style Java 21 / Spring Boot 3 microservices.
- Event-driven design with Kafka.
- Fuzzy name search with Elasticsearch.
- Explainable, versioned, auditable risk scoring.
- Streaming transaction monitoring with Kafka Streams.
- Analyst UI with React + TypeScript, backed by a GraphQL API.
- Automated tests at every level (unit, integration with Testcontainers, contract, end-to-end).
- CI with GitHub Actions; Docker Compose for local; Kubernetes manifests for deploy.
- Observability: metrics, logs, distributed tracing.
- A documented AI-assisted engineering workflow.

### Non-Goals
- No real regulatory certification or legal claims.
- No real customer data or live sanctions feeds.
- No production-grade identity verification (document OCR, liveness).

## 5. Architecture

### 5.1 Flow

```
 [UI / API client]
        │  POST /api/v1/customers
        ▼
 customer-service ──► Kafka: customer.onboarded
                              │
                  ┌───────────┴─────────────┐
                  ▼                         ▼
          screening-service           ownership-service
     (Elasticsearch fuzzy match)     (links to related parties)
                  │                         │
                  ▼                         ▼
      Kafka: screening.completed   Kafka: ownership.updated
                  └───────────┬─────────────┘
                              ▼
                        risk-service
              (score + reasons + audit trail)
                              │
                              ▼
                 Kafka: risk.assessed
                              ▼
                        case-service ──► GraphQL ──► UI (analyst console)
                              ▲
   Kafka: transactions.raw ──► txn-monitor-service ──► Kafka: alerts.raised
```

### 5.2 Kafka Topics

| Topic | Key | Value (JSON, versioned) | Partitions |
|---|---|---|---|
| `customer.onboarded` | customerId | CustomerOnboardedV1 | 3 |
| `screening.completed` | customerId | ScreeningCompletedV1 | 3 |
| `ownership.updated` | customerId | OwnershipUpdatedV1 | 3 |
| `risk.assessed` | customerId | RiskAssessedV1 | 3 |
| `transactions.raw` | accountId | TransactionV1 | 6 |
| `alerts.raised` | customerId | AlertRaisedV1 | 3 |
| `*.dlq` | original key | original value + error headers | 1 |

All events carry: `eventId` (UUID), `eventType`, `schemaVersion`, `occurredAt` (ISO-8601 UTC), `correlationId`, `payload`.

### 5.3 Cross-Cutting Rules
- **Idempotent consumers:** every consumer stores processed `eventId`s (table `processed_event` or Redis set with TTL) and skips duplicates.
- **Transactional outbox:** services that write to Postgres and publish to Kafka use an `outbox` table and a poller/relay so the DB write and the event never diverge.
- **Retries and DLQ:** consumers use exponential backoff (e.g. 3 attempts) and then publish to `<topic>.dlq`.
- **Correlation:** `correlationId` is propagated through HTTP headers, Kafka headers, logs (MDC) and traces.
- **Errors:** REST errors use RFC 7807 `application/problem+json`.
- **Config:** 12-factor; everything overridable by environment variables; no secrets in the repo.

## 6. Service Specifications

### 6.1 customer-service

**Responsibility:** Accept onboarding requests, validate, persist, emit `customer.onboarded`.

**REST API**
- `POST /api/v1/customers`: create a customer. Requires header `Idempotency-Key`. Same key + same body returns the original response; same key + different body returns `409`.
- `GET /api/v1/customers/{id}`
- `GET /api/v1/customers?status=&riskBand=&page=&size=`

**Customer model**
```
Customer {
  id: UUID
  type: INDIVIDUAL | COMPANY
  fullName: string            // legal name
  aliases: string[]
  dateOfBirth: date?          // individuals
  incorporationDate: date?    // companies
  nationality / countryOfIncorporation: ISO-3166 alpha-2
  addresses: Address[]
  identifiers: { type: PASSPORT|NATIONAL_ID|REGISTRATION_NO, value: string }[]
  status: PENDING_SCREENING | CLEARED | UNDER_REVIEW | REJECTED
  riskBand: LOW | MEDIUM | HIGH | null
  createdAt, updatedAt
}
```

**Tables:** `customer`, `customer_alias`, `customer_identifier`, `idempotency_record`, `outbox`.

**Rules**
- Name is trimmed and Unicode-normalized (NFKC).
- Reject future dates of birth; reject invalid country codes.
- Status transitions are enforced by a small state machine and illegal transitions throw a domain exception.

### 6.2 screening-service

**Responsibility:** Compare each customer against sanctions and PEP watchlists and emit match candidates with scores.

**Elasticsearch index `watchlist`**
```
{
  entryId, listType: SANCTIONS|PEP|ADVERSE_MEDIA,
  listSource, primaryName, aliases[], dateOfBirth?, countries[],
  entityType: INDIVIDUAL|COMPANY, addedAt
}
```
Analyzers: lowercase, ASCII-folding, and a phonetic filter (double metaphone). Use a `name` multi-field with `standard`, `phonetic` and `ngram` subfields.

**Matching algorithm (implement and unit-test each part)**
1. Normalize the customer name (lowercase, strip punctuation and honorifics such as "Mr", "Dr", "Sheikh"; transliteration-safe).
2. Query Elasticsearch: `bool.should` of `match` on `name` (fuzziness AUTO), `match` on `name.phonetic`, and `match_phrase` on aliases. Fetch top 20 candidates.
3. Re-score each candidate in Java:
   - **Name score (0–1):** weighted blend of Jaro-Winkler, token-sort ratio, and phonetic equality.
   - **DOB bonus:** exact +0.15, same year +0.05, conflicting year −0.20.
   - **Country bonus:** shared country +0.05.
4. Classify: `score ≥ 0.90` → `STRONG`; `0.75–0.90` → `POSSIBLE`; below → discard.
5. Emit `ScreeningCompletedV1` with all matches, each with `entryId`, `listType`, `score`, and a list of `matchedFields` (so risk-service can explain).

**Endpoints**
- `POST /api/v1/screen`: ad-hoc screening (synchronous, for the UI "quick check").
- `POST /api/v1/admin/watchlist/reindex`: reload the watchlist from the generator output.

**Tests:** table-driven tests of the scorer (typos, transposed names, name order swaps, transliteration variants, common-name false-positive cases), plus a Testcontainers Elasticsearch integration test.

### 6.3 risk-service

**Responsibility:** Combine signals into a risk score with human-readable reasons, version every model, and record an immutable audit trail.

**Inputs:** `ScreeningCompletedV1`, `OwnershipUpdatedV1`, customer attributes (fetched via REST or carried in the event), and the high-risk-country list.

**Scorecard model (v1, pure Java, deterministic)**

| Factor | Points |
|---|---|
| Strong sanctions match | +60 |
| Possible sanctions match | +25 |
| PEP match | +20 |
| High-risk jurisdiction (nationality or address) | +15 |
| Company with ownership depth > 3 layers | +10 |
| Owner is itself HIGH risk | +15 |
| Cash-intensive industry code | +10 |
| Missing key identifiers | +5 |

Bands: `0–29 LOW`, `30–59 MEDIUM`, `60+ HIGH`. Cap the score at 100.

**Explainability (required):** every assessment returns `reasons: [{factor, points, evidence}]` where `evidence` references the matched watchlist entry or the owner chain. The reason text must be generated from the data, not hardcoded.

**Model registry**
- Table `model_version(id, name, version, type: SCORECARD|ONNX, config_json, status: DRAFT|ACTIVE|RETIRED, created_at)`.
- Exactly one ACTIVE version per model name.
- `POST /api/v1/models/{id}/activate`; every assessment stores the `modelVersionId` used.

**Optional ONNX model (v2):** train a small logistic-regression or gradient-boosted model in Python on synthetic data, export to ONNX, load via ONNX Runtime Java. Keep the scorecard as a fallback and as a benchmark.

**Backtesting:** `POST /api/v1/models/backtest` takes two model versions and a labeled synthetic dataset, and returns precision, recall, confusion matrix and a list of customers whose band changed.

**Drift monitoring:** a scheduled job computes the score distribution per day and emits a Micrometer gauge; log a warning if the mean shifts beyond a configurable threshold.

**Audit log**
- Table `risk_audit(id, customer_id, model_version_id, input_snapshot_json, score, band, reasons_json, created_at)`; **insert-only**, enforced with a DB trigger that rejects UPDATE and DELETE.
- `GET /api/v1/customers/{id}/risk-history`.

**Emits:** `RiskAssessedV1`.

### 6.4 case-service

**Responsibility:** Turn risky assessments and alerts into analyst cases and manage review workflow.

**Case model**
```
Case {
  id, customerId, source: ONBOARDING|TRANSACTION_ALERT,
  priority: P1|P2|P3, status: OPEN|IN_REVIEW|ESCALATED|CLOSED_CLEARED|CLOSED_CONFIRMED,
  assignee?, slaDueAt, summary, evidenceRefs[], createdAt, updatedAt
}
CaseEvent { id, caseId, type, actor, comment, at }   // append-only timeline
```

**Rules**
- HIGH band → P1 (SLA 4h); MEDIUM → P2 (24h); alert-driven cases → P2.
- Auto-close LOW-band onboarding with no matches (no case created).
- A scheduled job escalates cases past `slaDueAt`.
- Closing requires a comment; decisions are recorded in `CaseEvent`.

**GraphQL schema (core)**
```graphql
type Query {
  cases(filter: CaseFilter, page: Int, size: Int): CasePage!
  case(id: ID!): Case
  customer(id: ID!): Customer
}
type Mutation {
  assignCase(id: ID!, assignee: String!): Case!
  addComment(id: ID!, text: String!): Case!
  closeCase(id: ID!, decision: Decision!, comment: String!): Case!
  escalateCase(id: ID!, reason: String!): Case!
}
type Subscription {
  caseCreated: Case!
}
```
Use DataLoader batching to avoid N+1 queries. The subscription runs over WebSocket (or SSE).

**Auth:** JWT (HS256 for local, configurable JWKS for real). Roles: `ANALYST`, `SENIOR_ANALYST`, `ADMIN`. Only `SENIOR_ANALYST` can close P1 cases as CONFIRMED.

### 6.5 txn-monitor-service

**Responsibility:** Detect suspicious transaction patterns in real time with Kafka Streams.

**TransactionV1**
```
{ txnId, accountId, customerId, amount, currency, type: DEPOSIT|WITHDRAWAL|TRANSFER,
  counterpartyAccountId?, counterpartyCountry?, channel, occurredAt }
```

**Rules (each is its own class implementing `DetectionRule`, with its own unit tests using `TopologyTestDriver`)**
1. **Structuring:** ≥ 3 cash deposits between 80% and 99% of the reporting threshold (default 10,000) within 24h for one customer.
2. **Velocity:** more than N transfers (default 10) in a 1-hour tumbling window.
3. **Rapid in-out:** inflow followed by ≥ 90% outflow within 2h (pass-through behavior).
4. **High-risk corridor:** transfers to or from countries on the high-risk list above a configurable amount.
5. **Dormant account spike:** a sudden large transaction on an account inactive for 90+ days (use a state store with last-activity time).

**Behavior**
- Rules are configurable via `application.yml` and hot-reloadable via an admin endpoint.
- Emits `AlertRaisedV1 { alertId, customerId, ruleId, severity, windowStart, windowEnd, txnIds[], explanation }`.
- De-duplicate alerts: the same rule and customer within a cooldown window raises only one alert.
- Handle late and out-of-order events using a grace period.

**Metrics:** `txn.processed`, `alerts.raised{rule}`, consumer lag, and p95 processing latency.

### 6.6 ownership-service

**Responsibility:** Model corporate ownership and answer "who really owns this company?"

**Tables**
```
entity(id, type: PERSON|COMPANY, name, country, customer_id?)
ownership_edge(parent_id, child_id, share_pct, effective_from, effective_to?)
```

**Capabilities**
- `GET /api/v1/entities/{id}/ultimate-owners?threshold=25` returns the ultimate beneficial owners (UBOs). Multiply percentages along each path, sum per person, and filter by threshold. Use a PostgreSQL recursive CTE.
- **Cycle detection:** circular ownership must not hang the query; track the visited path.
- `GET /api/v1/entities/{id}/graph?depth=` returns nodes and edges for the UI visualization.
- Risk propagation endpoint: given per-entity risk bands, return the maximum risk reachable within N hops.
- Emits `OwnershipUpdatedV1` when edges change.

**Tests:** known fixtures (a simple chain, diamond ownership, circular ownership, a 5-level shell structure) with expected UBO percentages.

### 6.7 UI (React + TypeScript)

**Screens**
1. **Login:** JWT; role-aware navigation.
2. **Case queue:** filter by priority, status and assignee; SLA countdown badges; live updates via the GraphQL subscription.
3. **Case detail:** customer profile, risk score with the **reasons breakdown**, screening matches side by side with the watchlist entry, ownership graph, case timeline, and action buttons (assign, comment, escalate, close).
4. **Quick check:** type a name, see fuzzy matches and scores instantly.
5. **Model admin (ADMIN):** list model versions, activate, run backtest and show the confusion matrix.
6. **Ownership explorer:** an interactive graph (React Flow) with UBO highlighting.

**Standards:** accessible (labels, keyboard navigation, ARIA), responsive, loading and error states everywhere, no `any` in TypeScript, Vitest component tests, one Playwright end-to-end test covering "onboard a risky customer → case appears → analyst closes it".

## 7. Data Model Conventions
- UUID primary keys; `created_at` / `updated_at` as `timestamptz`.
- Flyway migrations named `V<n>__description.sql`; never edit applied migrations.
- Money as `NUMERIC(19,4)` with an ISO-4217 currency column; never floating point.
- Each service owns its own schema (`customer`, `risk`, `case`, ...) and no service reads another service's tables.

## 8. Security Requirements
- JWT validation on all APIs; role checks with method security.
- Input validation (Jakarta Validation) on every request DTO.
- PII masking in logs (mask names and identifiers); never log full request bodies.
- Secrets via environment variables or Kubernetes Secrets.
- Rate limiting on public endpoints with a Redis token bucket (the `Retry-After` header on `429`).
- Dependency scanning in CI (OWASP Dependency-Check or Dependabot) and container image scanning (Trivy).

## 11. Synthetic Data Generator (`data-generator`)

A CLI (Spring Boot `CommandLineRunner` or a plain Java main) with these commands:
- `watchlist --count 50000`: fake sanctions/PEP entries with aliases, DOBs and countries; include deliberate near-duplicates and transliteration variants.
- `customers --count 10000 --risky-ratio 0.03`: customers, a known fraction of whom are intentionally fuzzy variants of watchlist entries (so you have ground truth for backtesting).
- `transactions --customers 10000 --days 30`: normal behavior plus injected patterns (structuring, rapid in-out, velocity) with labels.
- `ownership --companies 2000 --max-depth 6`: random ownership trees, including cycles and diamonds.

Use a fixed seed option for reproducible tests. Output goes to JSON/CSV files and can be posted to the APIs or Kafka.
